# QueryForce

QueryForce is a natural language interface for your database. You type a question in plain English — it figures out the SQL, runs it securely, and gives you a clear answer.

No SQL knowledge required. No dashboards to configure. Just ask.

---

## The Problem

Most people who need data from a database can't write SQL. And most people who *can* write SQL spend half their time on boilerplate — joins, aggregations, date filters — for questions that should take five seconds to answer.

There's also a darker problem: if you give users direct database access, they can run queries that take down your server. Cartesian products, unindexed full-table scans, `DROP TABLE` — it happens.

QueryForce sits between the user and the database. It translates, guards, and explains.

---

## What It Does

You type: *"Who are our top 10 customers by order volume this year?"*

QueryForce:
1. Figures out which tables are relevant to your question (using semantic vector search, not keyword matching)
2. Injects any business rules — so "revenue" maps to the right column, and "active customer" means what your business actually defines it to mean
3. Generates SQL using an LLM, then runs it through two layers of validation before it ever touches the database
4. Executes the query in strict read-only mode, streaming results back in chunks
5. Synthesizes the raw results into a plain English answer

The whole flow — routing, SQL generation, validation, execution, synthesis — runs as a graph of steps that can retry automatically if something goes wrong.

## Features

**Natural language to SQL**
Ask questions the way you'd ask a colleague. The system handles table selection, joins, aggregations, and filters automatically.

**Semantic schema routing**
Uses ChromaDB vector embeddings to find the relevant tables for your question — not just keyword matching, but actual semantic similarity. If your question is about "income", it finds the right column even if it's called `total_amount`.

**Business rule injection**
Define your own metric definitions in `data/metrics.yaml`. When you ask about "revenue" or "active customers", the system injects the correct formula before generating SQL.

**Conversational memory**
Each session remembers what you've discussed. You can define a formula in one message ("treat profit as 30% of total_amount") and use it in the next. Sessions persist across page loads.

**Two-model cross-checking**
SQL is generated by two separate model instances (one deterministic, one with slight variation). The first candidate that passes the AST validator wins. This quietly improves quality without slowing things down.

**Hard security layer**
Every generated SQL is parsed into an Abstract Syntax Tree before execution. The validator blocks:
- Any DDL or DML (CREATE, DROP, INSERT, UPDATE, DELETE)
- PRAGMA statements
- Cross joins and cartesian products
- Queries referencing tables that don't exist in the schema
- Queries exceeding 500 rows without an explicit LIMIT

If the LLM asks for something that doesn't exist in the schema — a "profit" column when none exists — the system refuses cleanly rather than hallucinating a number.

**Anti-hallucination prompting**
The SQL generation prompt explicitly instructs the model to output a sentinel value (`SELECT 'METRIC_NOT_FOUND' AS error`) if it's asked for a metric that has no corresponding column. The synthesizer catches this and returns an honest message.

**Streaming responses**
Results stream back to the UI via Server-Sent Events. You see the SQL preview, confidence score, and query latency in real time while the answer is being synthesized.

**Rate limiting**
10 requests per minute per IP. The underlying Groq API quota is protected.

**CSV export**
Any result set can be exported as a CSV with one click.

## How to Run It

### Prerequisites
- Python 3.11+
- A Groq API key (free tier works fine): https://console.groq.com
- Your own API key for the app (any string — this is the key users enter to access the app)

### Setup

```bash
# Install dependencies
pip install -r requirements.txt

# Copy the example env file and fill in your keys
cp .env.example .env
```

Your `.env` file needs:
```
GROQ_API_KEY=your_groq_key_here
QUERYFORCE_API_KEY=any_secret_string_you_choose
```

### Seed the database and vector store

```bash
python scripts/ingest_schema.py
```

This reads your database schema and loads it into ChromaDB so the semantic router knows which tables exist.

### Run

```bash
uvicorn src.api.server:app --reload
```

Open http://localhost:8000 and enter your `QUERYFORCE_API_KEY` when prompted.

### Docker

```bash
docker build -t queryforce .
docker run -p 8000:8000 --env-file .env queryforce
```

## Configuration

**`data/metrics.yaml`** — define business metric aliases and rules:
```yaml
revenue:
  aliases: ["income", "sales", "earnings", "total revenue"]
  rule: "Revenue is calculated as SUM(total_amount) from the orders table"

active_customer:
  aliases: ["active user", "engaged customer"]
  rule: "An active customer has placed at least one order in the last 90 days"
```

The system uses these to both route queries semantically (via ChromaDB) and inject context into the SQL generation prompt.

**`src/config.py`** — all runtime settings via environment variables:
- `LLM_SQL_MODEL` — model used for SQL generation (default: `llama-3.3-70b-versatile`)
- `LLM_SYNTH_MODEL` — model used for answer synthesis (default: `llama-3.1-8b-instant`)
- `MAX_RETRIES` — how many times to retry failed SQL before giving up (default: 2)
- `HYDE_CONFIDENCE_THRESHOLD` — confidence cutoff below which HyDE retrieval kicks in (default: 0.4)
- `CORS_ALLOWED_ORIGINS` — comma-separated list of allowed frontend origins

## Connecting to a Real Database

QueryForce ships with a sample SQLite database for demonstration. To connect it to a real database (e.g., AWS RDS PostgreSQL), see the migration architecture document in the `MD/` folder. The short version:

1. Replace `aiosqlite` with `asyncpg` (already commented in `requirements.txt`)
2. Create a database user with `SELECT`-only permissions — never use your admin credentials
3. Update `ANALYTICS_DB_PATH` with your PostgreSQL DSN
4. Update `src/db/executor.py` and `src/db/inspector.py` to use the new driver

The security model (read-only enforcement, query timeout, cartesian product detection) carries over — it just needs to be implemented at the connection level rather than the SQLite URI level.

## Architecture

```
User question
    │
    ▼
Intent Router (LLM) ──► Document RAG path (for uploaded PDFs/CSVs)
    │
    ▼ schema_rag
Business Rules Injection (ChromaDB synonym matching)
    │
    ▼
Schema Retriever (ChromaDB semantic search → relevant tables)
    │
    ├── confidence too low? → HyDE Retriever (hypothesis-based re-retrieval)
    │
    ▼
SQL Generator (LLM × 2 candidates, cross-checked)
    │
    ▼
AST Validator (sqlglot — blocks DDL, DML, PRAGMA, bad joins, table hallucinations)
    │
    ├── validation error? → retry → SQL Generator (up to MAX_RETRIES)
    │
    ▼
Query Executor (read-only, chunked streaming, 3s timeout, DoS detection)
    │
    ▼
Answer Synthesizer (LLM — translates raw results to plain English)
    │
    ▼
Session Memory (DynamoDB / local fallback)
    │
    ▼
SSE Stream → UI
```

## Stack

| Layer | Technology |
|---|---|
| API | FastAPI + uvicorn |
| Pipeline orchestration | LangGraph |
| LLM | Groq (Llama 3.3 70B for SQL, Llama 3.1 8B for synthesis) |
| Vector store | ChromaDB + ONNX MiniLM embeddings |
| SQL validation | sqlglot (AST parser) |
| Database | SQLite (production: swap for PostgreSQL) |
| Session memory | AWS DynamoDB (local dict fallback) |
| UI | Vanilla HTML/CSS/JS, Server-Sent Events |
| Rate limiting | slowapi |
| Deployment | Docker → Railway |
